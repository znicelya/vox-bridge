# Task 5: credential-operation ownership handoff

Static integration analysis, 2026-11-06. Reviewed 3A/3B APIs plus the current, in-progress 4B boundary; **future Task 5 risk**, not a completed-handler defect or a broader review. No source changes, native/keyring calls, network, Cargo, or tests were performed. Source references below are relative to `src-tauri/src`; 4B line numbers describe the inspected working-tree snapshot.

**Finding:** an unscoped future handler can return after its credential observer times out while blocking credential work continues beyond scheduler-generation completion and, after remaining application owners drop, physical `app.lock` ownership.

- `ServiceConfigStore::scoped(OperationLease)` forwards ownership to ConfigIo (`intelligence/config.rs:30–34`). Existing resolution APIs are `probe_snapshot(id)` (`:36–61`) and `resolve_credentials(id)` (`:273–291`); `resolve_snapshot_credentials` does not exist in reviewed commit `5a0d676` or the inspected paths. The latter reads the currently saved profile and calls `tx.secret_get`; it does not validate an admitted immutable profile snapshot.
- ConfigIo defaults to no owner (`config/worker.rs:58–65`). `with_operation_owner` supplies one (`:87–90`); `run` moves its cloned owner and config permit into `spawn_blocking` (`:103–118`). Cancellation suppresses the callback only before entry (`:122–140`). Once entered, the callback can continue after the observer deadline (`:148–157`). The timeout currently becomes an Intelligence Configuration error through `safe_config_error` (`intelligence/config.rs:351–355`), not the typed Timeout code.
- A read can have late side effects: `secret_get` takes the secret transaction lock (`config/worker.rs:203–205,248–251`); that lock can create a directory/file (`config/secret_store.rs:137–146`). `get_locked` returns early when no ciphertext exists, otherwise calls `load_or_create` (`:170–183`); OS keyring `NoEntry` creates a DEK via `set_password` (`:24–40`). This does not imply every read creates a key.

**Physical lock retention and acknowledged shutdown are separate.** `OperationLease` is erased `Arc<dyn Send + Sync>` (`intelligence/jobs.rs:71`), but `AppState::start_intelligence` actually passes only `_process_lock.clone()`, an `Arc<File>` (`app/intelligence.rs:8–12`; `app/mod.rs:54–56`). Generation ownership holds that lease, waits workers/handler cleanup, then drops it and publishes completion (`intelligence/jobs.rs:147–187`). `JobContext` exposes only id, cancellation and admission fence (`:22–34`); no actual-operation lease reaches a timed-out blocking credential task. Successful scheduler shutdown clears the generation (`:369–397`).

The existing application operation token instead owns both process lock and semaphore permit (`app/intelligence.rs:3–5,19–29`). `close_all` waits scheduler/probe/subscription shutdown, then acquires all 16 operation permits before acknowledging success (`app/lifecycle.rs:203–225`). A mere extra `Arc<File>` neither participates in this quiescence barrier nor delays generation completion; it can keep the file locked while the same AppState becomes eligible to rearm.

**Smallest proposed Task 5 owner port:** give `JobContext` a narrow accessor issuing a generation-tracked child operation token, carrying the generation's process lease and a counted drain guard. Register acquisition against the stopping fence; pass an ephemeral `config.scoped(context.operation_owner()?)` to credential resolution. Existing ConfigIo then retains the token through actual blocking completion. After workers and cleanup finish, the generation must await child-operation drain before dropping its base lease or publishing completion. This makes existing scheduler shutdown—and consequently `close_all`—acknowledge actual completion; timeout keeps rearm fenced. Keep handlers/config stores unscoped at rest; never capture AppState or the scheduler. Future snapshot resolution must separately validate the admitted public profile under the same config gate.
