## Findings that affect implementation

1. **The pinned `SrvDB` is Send + Sync.** A non-Send/Sync premise is incorrect for this revision. Keep one dedicated owner because Task 5 requires serialized operations, lifecycle control and exclusive directory ownership, not because this type cannot cross threads.
2. **Default construction starts Flat and does not enable automatic migration.** `set_mode(IndexMode::Auto)` is the explicit automatic-index API. It preserves full-precision storage; a controller should resolve whether Task 5's automatic-behaviour sentence requires this additional call on every open.
3. **Bounded metadata scans are feasible, but `None` is not synonymous with tombstone.** Check `is_deleted(id)` separately; a live ID with missing metadata is a repair condition. Keep only owned batch results and cursor/lease state across yields.
4. **There is no vector getter on `SrvDB`.** The exported `VectorStorage` provides full-precision borrowed reads. An existing-file reader can be used under a frozen source owner retaining `srvdb.lock`; no second `SrvDB` may open the source directory. Building the destination through real `add_batch`/`persist` still requires a separate engine for the new generation, so the plan needs an explicit generation-overlap interpretation.
5. **200000 records and two identities give a large finite storage bound, not a small RAM budget.** At 4096 dimensions, logical vector bytes are about 3.28 GB per identity. File growth slack, redb caches, optional graphs, temporary copies and rebuild overlap are additional. Internal Rayon work must also be bounded explicitly.

## Owner, open, close and persistence

Exact source evidence:

- `S/src/engine/mod.rs:48–79`: concurrency documentation states `Send + Sync`, exclusive OS `srvdb.lock` lifetime, shared search and exclusive mutable writes. `S/tests/test_concurrency.rs:41–45` contains the compile-time `assert_send_sync::<SrvDB>()`; `:47–58` tests same-directory rejection and successful reopen after drop. These are source evidence, not test executions in this preflight.
- `S/src/storage/lock.rs:26–45`: `File::try_lock()` is exclusive and nonblocking; `WouldBlock` becomes `Error::Locked`. The owned `File` holds the lock. `:1–6` documents process-exit/crash release; no stale-lock-file deletion is necessary.
- `S/src/engine/open.rs:10–16,55–62`: opening creates the directory, takes the lock, opens metadata, recovers vector state and may attach saved graphs. It is a writable recovery operation, not a read-only filesystem inspection.
- `S/src/storage/metadata.rs:47–70`: open may create tables, upgrade older metadata storage, finish committed compaction or discard abandoned compaction files. `S/src/engine/recover.rs:11–42` truncates uncommitted vectors/metadata and eagerly loads tombstones into the engine `HashSet`.
- There is no public `close` or engine `Drop` persistence hook. Drop releases fields/locks; it does not call `persist`. `S/tests/test_recovery.rs:42–62,80–89` demonstrates unpersisted writes being discarded on reopen; `S/tests/test_delete.rs:100–114` demonstrates an unpersisted delete being undone.
- `S/src/engine/commit.rs:6–37`: auto migration first, vector fsync second, durable redb count/metadata/tombstones commit third, derived graph files last. `S/src/storage/metadata.rs:94–103,162–179` distinguishes non-durable metadata sets from `Durability::Immediate` commit. **A `persist()` error can occur after vectors/metadata are already durable**, if a later graph save fails. SQLite must remain non-Ready on every failure; recovery must tolerate already-committed mutations.
- `S/src/engine/write.rs:83–107,110–145`: insertion appends vectors, indexes IDs, then sets metadata. A fallible insert is not an all-or-nothing application transaction; partial appends and partial metadata writes are possible after initial validation. Reconcile before retrying, and never infer “no mutation occurred” from an error.

Minimal facade: `Arc<IndexOwner>` contains a bounded sender (capacity 16), lifecycle/shutdown state and a join handle, not public database references. The dedicated blocking thread opens and owns the engine map keyed by `(identity, generation)`. Owned vectors, metadata DTOs, IDs and response channels cross the queue. Every command performs its bounded mutation and explicit persistence as one owner phase; successful vector persistence is reported before the separate SQLite Ready transaction. Network embedding calls stay outside this owner.

Keep a dirty/repair outcome in owner state. Do not use LRU eviction or shutdown as an implicit commit of arbitrary failed operations, and do not report an unpersisted mutation as saved. An explicit successful mutation command normally leaves a clean engine; eviction drops an idle clean engine. A failed/dirty engine can instead be closed and reopened to recover its last durable state, followed by SQLite-led reconciliation. Shutdown rejects new work, observes bounded completion/cancellation and joins the owner; `Drop` alone is not a recoverable persistence protocol.

## Exact full-precision and automatic-mode configuration

The Task 5 constructor snippet is valid for a Flat start:

```rust
let mut config = DatabaseConfig::new(identity.dimensions as usize)?;
// Defaults already have these values; explicit assignment makes policy clear.
config.index_type = srvdb::IndexType::Flat;
config.quantization.enabled = false;
config.quantization.mode = srvdb::QuantizationMode::None;
let mut db = SrvDB::new_with_config(path, config)?;
// Add this only under the controller's automatic-index interpretation:
db.set_mode(srvdb::IndexMode::Auto);
```

Evidence: `S/src/config.rs:19–23,78–87`; `S/src/engine/open.rs:18–35,43–49`. Disabled quantization uses `vectors.bin` f32 storage. Do not call SQ8/PQ constructors, `auto_tune_pq`, `set_mode(Sq8)` or `set_mode(Ivf)` for Task 5. The crate validates dimensions/finite values, but its vector validation does not reject zero norm and `Vector::normalize()` is unchecked f32 accumulation; keep Task 5's checked normalization in the embedding adapter (`S/src/engine/validate.rs:10–22`; `S/src/vector.rs:20–27`). Metadata validation checks JSON syntax only, with no schema or byte limit (`S/src/engine/validate.rs:33–38`); bound the application's location fields and encoded metadata.

`set_mode(Auto)` is public (`S/src/engine/modes.rs:10–15`), and its automatic strategy never converts storage (`S/src/tuning/auto_tune.rs:1–7,29–43`). Migration during `persist()` is gated on `current_mode == Auto` (`:21–27`). Default construction leaves `current_mode == Flat`, so that hook otherwise does nothing. Auto's default threshold is 50000 stored records and at least 2 GB of detected total system RAM (`S/src/tuning/strategy.rs:51–57,72–88`); Linux detection uses `MemTotal`, not currently free memory, with a 4 GB fallback elsewhere (`S/src/tuning/auto_tune.rs:46–69`). Count includes tombstones, so graph construction can be triggered by deleted-record accumulation.

Saved `hnsw.graph` attaches regardless of a new Flat config, and saved IVF also attaches (`S/src/engine/open.rs:57–62`). Reopening a saved HNSW selects `Hnsw`; restore `Auto` explicitly if the policy is automatic (`:87–101`). `set_mode(Flat)` only changes flags and does not drop a previously attached graph (`S/src/engine/modes.rs:19–26`); the search path selects existing graph fields first (`S/src/engine/read.rs:9–28`). Avoid promising permanent exact-flat behaviour or manipulating existing graph files to enforce it.

## Bounded scanning and idle yields

Exact range semantics are already correct in the plan:

- `S/src/storage/record_file.rs:124–136`: append returns prior count; `S/src/storage/flat.rs:50–57` returns the half-open batch range. `S/src/engine/mod.rs:142–151` supplies stored-record count. `S/src/engine/delete.rs:14–28` rejects `id >= count`, and `:56–59` defines live count.
- `S/src/engine/mod.rs:131–135`: `get_metadata` returns `None` immediately for a tombstone, otherwise queries metadata. `S/src/storage/metadata.rs:123–127` owns the returned `String`; its redb transaction/table/value guards die before return. Out-of-range IDs are not validated by this method and may also return `None`.
- `S/src/engine/delete.rs:52–54` exposes `is_deleted`. `S/src/storage/metadata.rs:165–176` removes persisted tombstone metadata, but an unpersisted delete's metadata remains physically present while the engine masks it.
- `all_metadata` collects the whole metadata table before filtering (`S/src/engine/commit.rs:40–44`; `S/src/storage/metadata.rs:144–155`); it is unsuitable for normal bounded reconciliation.

Suggested owner scan state: `(identity, generation, snapshot_end: u64, next_id: u64, lease_token)`. Capture `snapshot_end = db.count()` inside the owner and reject unsupported count before scanning. Each step examines at most 200 **stored IDs**, including tombstones. Compute the next half-open end with checked u64 arithmetic; never collect `0..count()` into a vector. Return owned rows `{id, deleted, metadata}` and the next cursor. A nondeleted ID whose metadata is absent/malformed must be reconciled through SQLite's inverse `(identity, generation, vector_id)` mapping; it must not be silently skipped as a tombstone.

Release every map-entry borrow, database reference, metadata guard and borrowed vector slice before an idle yield, queue wait, SQLite work or response send. Only cursor/lease state and bounded owned data survive. This is a lifecycle/remap restriction, **not** a non-Send/Sync restriction: `VectorStorage::get/get_batch` borrow mmap bytes (`S/src/storage/flat.rs:86–96`); append can unmap/remap and reopen/drop can replace the owner (`S/src/storage/record_file.rs:127–132,193–223`).

A captured count fixes the scan boundary, not the entire metadata/SQLite snapshot. Use a per-generation maintenance lease that delays same-generation mutations, rebuild and LRU close while permitting unrelated identity commands between batches. Alternatively, every batch/result needs generation and row-version validation plus restart rules; the lease is simpler. Do not hold a SQLite transaction across the scan or an embedding request. Cancellation drops the lease/cursor after the current bounded step.

Missing or malformed metadata cannot name a document by itself. Use the inverse SQLite mapping to mark affected documents RepairRequired. If no authoritative document owns the record, treat it as an orphan for local tombstone cleanup; never fabricate a document ID. Search metadata enrichment also suppresses metadata read errors into absent metadata (`S/src/engine/read.rs:84–93`), so a search success alone does not prove readiness. Authoritative hydration and readiness checks remain mandatory.

Metadata presence does not inspect vector contents. Recovery detects a committed count larger than physically present records, but does not validate every stored f32/norm (`S/src/engine/recover.rs:20–40`; `S/src/storage/record_file.rs:79–87`). Where startup reconciliation requires per-record content validation, use the same frozen full-precision reader described below and copy/check vectors in bounded batches; do not claim `get_metadata` detects a corrupted/zero/nonfinite vector by itself.

## Vector-preserving generation rebuild without compact

`VectorEngine` exposes no get/export vector method (`S/src/engine/mod.rs:35–45`); engine storage fields are crate-private (`:61–64`). `VectorStorage` is publicly exported (`S/src/lib.rs:18,29`) and its read methods are sufficient for the full-precision policy (`S/src/storage/flat.rs:86–96`). Do not reembed healthy records merely to recover tombstone capacity.

Opening **an existing, nonzero** vector file via `VectorStorage::new` does not change file length, vector bytes or metadata: constructor computes record size and calls `RecordFile::open` (`S/src/storage/flat.rs:23–29`), which opens read+write, validates the header, reads file length/count and maps the file (`S/src/storage/record_file.rs:49–92,214–223`). However, it creates a missing/zero-length file (`:49–53,95–99`) and takes **no directory lock**. It is not a general read-only database API.

Suggested frozen-source reader, subject to the overlap ruling below:

1. Hold the source `SrvDB` in the same owner, retaining its OS directory lock. Acquire a source-generation maintenance lease; complete persistence successfully before opening the reader. Check the existing vector file is nonzero, reader dimension/count equal the identity/source count, and the generation/SQLite desired rows are stable. No source `add`, `replace`, `delete`, `persist`, `compact`, close or resize may run while the reader is alive. The source engine supplies `is_deleted/get_metadata`; no second `SrvDB` or `MetadataStore` opens the source directory.
2. Create a distinct managed staging generation using real `SrvDB::new_with_config` with the same full-precision policy. Copy only authoritative Ready chunks whose source ID, metadata/version/hash and identity match. In batches of at most 200, read `VectorStorage::get(id)` (or contiguous `get_batch`), immediately `to_vec()` each retained slice, validate finite/nonzero/correct-dimensional values, and retain owned metadata. Preserve f32 values exactly; do not normalize them again during copying. Borrowed slices disappear before destination mutation or yielding.
3. Call destination `add_batch`; zip returned IDs to the selected chunk rows only after checking returned lengths. Stage `(identity, new_generation, chunk_id, old_id, new_id, version, hash)` mappings in SQLite in bounded transactions. Do not retain all mappings in a process `Vec` or update the currently active mappings incrementally.
4. Persist destination, validate it in bounded passes and reopen validation if required. Switch generation pointer and publish every new mapping in **one SQLite transaction**, conditioned on the source generation/version fence. A generation-keyed mapping table allows staging batches followed by pointer publication; all search/hydration queries must join the active generation. If the existing schema insists on vector IDs directly in active chunk rows, its atomic publication strategy must be settled before implementing rebuild.
5. After successful publication, drop the low-level reader and old source engine before deleting the old managed directory (Windows mapped-file handles matter). On cancellation or failure before publication, the old pointer/files remain authoritative; discard or resume the unreferenced staging generation locally. After pointer commit, failed old-file cleanup is a durable cleanup intent, not a rollback to old IDs.

Never call source `compact`: it commits first, densely renumbers IDs and returns only removed count (`S/src/engine/compact.rs:7–24,38–65`). There is no public old-to-new mapping result. The whole-vector-file copy helper is crate-private (`S/src/storage/flat.rs:66–69`) and does not replace application mapping publication.

The same-file auxiliary mmap is safe only under the freeze/retained-lock conditions above. It adds another virtual mapping of the source file, usually backed by the same physical file pages; do not count it as a guaranteed second physical copy or allow writes on that reader. Its public type exposes mutation methods, so keep it private inside a reader-only adapter.

## Actual memory, lock and capacity consequences

| Component | Source-backed implication at the Task 5 limit |
| --- | --- |
| Full-precision logical vector file | `24 + stored_count * dimensions * 4` bytes (`S/src/storage/header.rs:35–37`; `S/src/storage/flat.rs:25,99–102`). At 200000: 102400024 bytes for 128 dimensions; 3276800024 bytes for 4096 dimensions. Two maximum-dimensional identities have 6553600048 logical vector bytes. These are arithmetic storage values, not RSS measurements. |
| Allocated/mapped file slack | Append grows by max(half current capacity, 1024 records), mapping the **whole allocated file**, not logical count (`S/src/storage/record_file.rs:79–91,124–132,214–223`). Ordinary capped append sequences can approach 1.5 times logical capacity at these limits. `persist` does not trim slack; reopen/recovery truncates to committed logical length (`S/src/engine/recover.rs:31–40`; record file `:193–211`). |
| Tombstones | Vector bytes and existing graph nodes remain. The engine retains a `HashSet<u64>` plus pending-delete `Vec<u64>` (`S/src/engine/mod.rs:74–77`); recovery temporarily collects all tombstone IDs before building the set (`S/src/storage/metadata.rs:249–253`; recover `:41`). Bounded under the stored-record cap, but not limited to 200 IDs merely because reconciliation uses 200-ID batches. |
| Metadata | SrvDB opens redb with `Database::create` and no cache configuration (`S/src/storage/metadata.rs:26–38,77–89`). The locked redb tag defaults to a **1 GiB maximum page-cache setting per database**, initially empty caches, not a 1 GiB eager allocation; cache indices/guards/transaction allocations are additional (supplemental references below). Two open engines have up to two such cache budgets; rebuilding with a third engine would add another. Metadata JSON bytes are not bounded by SrvDB validation. |
| HNSW | Fully resident `HashMap<u64, HNSWNode>` behind `Arc<RwLock>`; each node owns nested neighbor vectors (`S/src/index/hnsw/mod.rs:84–109,150–163`). Opening reads serialized graph bytes then deserializes a full graph (`S/src/engine/open.rs:71–101`); persistence holds graph state plus serialization output (`S/src/index/hnsw/mod.rs:206–231`). No exact per-record/RSS guarantee follows from the documentation's approximate byte claims. |
| Flat search | Candidate limit 100 does not cap internal work/storage. It touches stored-record batches and collects all live `(u64,f32)` scores before selecting top-k (`S/src/distance/mod.rs:84–111`), with additional transient top-k/batch allocations. At 200000 records this is a full-library operation on one owner. |
| Rebuild | Source vector file and new vector file coexist until pointer publication/cleanup; staging SQLite mappings and destination metadata/graph coexist too. Budget disk before starting, close the other idle identity to keep at most two engine instances during overlap, and account for the auxiliary source mmap. Disk-full/persist failure must preserve the old generation. |

The supported limit must be enforced by the adapter: the crate has no 200000-record cap. Before **each** add/replace/batch, check `count.checked_add(new_record_count) <= 200000` inside the owner. Replacement consumes an additional stored record; deletion does not free capacity. Reserve a whole application's intended batch before mutating so a mid-document cap failure does not create avoidable partial work. Do not use live count or queue length as the capacity check.

An existing engine has already mapped its file and loaded tombstones/graphs by the time `count()` can be checked. For the plan's open-memory bound to apply to externally damaged/oversized managed files too, reject oversized headers/files before writable open and treat unsupported generations as repair-required; never truncate committed data to fit a budget. The maximum normal allocation slack must be allowed by that precheck. The exact anomaly-handling and metadata/graph file-size bounds need a controller-approved policy rather than claims that the record cap alone covers arbitrary on-disk files.

Locks are layered: the mandatory outer `srvdb.lock` prevents duplicate SrvDB opens; redb also locks its metadata backend and uses cache/transaction synchronization; HNSW has internal `parking_lot::RwLock`s. Do not introduce an extra application `Mutex<SrvDB>` used from arbitrary async tasks. One owner provides serialization while those internal locks remain implementation details.

- [`v4.4.0 src/db.rs:2031–2046`](https://github.com/cberner/redb/blob/v4.4.0/src/db.rs#L2031): `Builder` default 1 GiB cache and `ExclusiveWriter`; public builder cache setter at `:2079–2082`. SrvDB's public constructor does not expose it.
- [`cached_file.rs:282–297`](https://github.com/cberner/redb/blob/v4.4.0/src/tree_store/page_store/cached_file.rs#L282) describes read/write cache sharing; [`:338–358`](https://github.com/cberner/redb/blob/v4.4.0/src/tree_store/page_store/cached_file.rs#L338) initializes empty striped LRU caches/counters. Eviction is best effort under outstanding references (`:905–951`), so the configured page-cache limit is not a total process heap guarantee.
- [`page_manager.rs:680–729`](https://github.com/cberner/redb/blob/v4.4.0/src/tree_store/page_store/page_manager.rs#L680) selects whole-backend exclusive locking and rejects an already-open backend; `:1039–1042` connects this to cache/open lifetime. Unsupported backend locks can be tolerated by redb, but the outer SrvDB OS lock is still required.

## Internal worker bounds

No production `std::thread::spawn`/dedicated background thread creation was found in the targeted SrvDB engine/storage/index/quant/distance/tuning source. **There is more Rayon than just Flat distance search**: engine multi-query read (`S/src/engine/read.rs:105–110`), IVF writes/training (`engine/write.rs:70–76`, `engine/modes.rs:111–117`, `index/ivf.rs:99–100`), IVF serialization (`storage/ivf.rs:36–41`), hybrid search (`index/hybrid.rs:105`), and PQ/codebook training/search (`quant/product.rs:57`, `quant/codebook.rs:41`, `distance/quantized.rs:27,53`). Quantized/IVF modes are outside the requested policy, but saved IVF files can attach on open.

The inspected redb open/cache/page-manager paths perform allocation, locking and flush work in the caller; matching thread-spawn sites in those files are tests. Its platform file backend selects optimized backends on Windows/Unix (`v4.4.0 src/tree_store/page_store/file_backend/mod.rs:1–13`); [`optimized.rs:315–375`](https://github.com/cberner/redb/blob/v4.4.0/src/tree_store/page_store/file_backend/optimized.rs#L315) performs synchronous positional read/write and `sync_data`, with no production background spawn in that file. This is a focused path audit, not a claim that every transitive dependency has been exhaustively audited.

Minimal bound: build one owner-scoped Rayon pool with `num_threads(2)` and run every SrvDB open/search/mutation/persist/rebuild-validation call through `pool.install`. Nested crate parallel iterators then use that pool rather than initializing/using the host-wide CPU-count pool. Keep normal search to the single-query engine API; do not multiply Task 5's two outstanding searches into unbounded library batch searches. Count the dedicated owner plus two Rayon workers explicitly. A synchronous crate call has no cancellation callback; cancellation can be observed before/after the call and between batches, not interrupt graph construction/fsync. Do not promise a deadline or kill/release its locks while a call is still running.

## Focused real-index tests recommended

Default tests use actual SrvDB with 128-dimensional synthetic vectors, local SQLite/temp paths and deterministic embeddings. This preflight ran none of them.

- **Owner lifecycle/lock:** commands execute on the same owner; a duplicate source-directory open gets Locked; a third identity evicts only an idle clean owner; drop/reopen retains persisted writes, discards unpersisted writes and restores an unpersisted delete. Shutdown/LRU cannot silently convert failed dirty work into Ready data.
- **Scan boundary and absence:** at least 401 stored records spanning multiple 200-ID batches, live IDs 0 and count-minus-one, tombstones at a batch boundary, missing metadata on a live ID, and count excluded. Verify cursor steps examine <=200 IDs and classify missing metadata independently from tombstones. Interleave unrelated identity commands; a leased source mutation/close must wait. Cancellation releases the lease without any outstanding borrowed DB state.
- **Post-commit failure:** retain Task 5's four crash injection points; additionally test an adapter-observed `persist` error after underlying durability (e.g. test fixture derived-index save failure). Reopen and reconcile from SQLite intent without exposing an uncommitted document or assuming the vectors vanished. Cover a failed add leaving an orphan and duplicate retry.
- **Generation mapping and vector preservation:** source IDs with gaps/tombstones, retained first and last IDs, distinct metadata and non-axis full-precision vectors. Rebuild through destination `add_batch`, compare f32 bit patterns through frozen storage reads, stage returned IDs, reopen destination and validate SQLite mappings. Query after pointer swap must hydrate new IDs only, while old metadata/version cannot leak. Embedding call count remains unchanged.
- **Generation crashes/cleanup:** before destination persist, after destination persist before SQLite pointer commit, after pointer commit before old-file deletion. At every reopen exactly one published generation wins with a complete mapping set. Cancellation/disk-full keeps the only good generation. Old source engine/auxiliary reader handles are dropped before directory removal; test two-instance overlap policy with another cached identity.
- **Capacity:** configure a small test-only adapter record limit to prove count-including-tombstones, whole-batch reservation, replacement extra-slot consumption, no ID reuse without generation change, visible import failure at capacity, and recovered capacity after generation rebuild. Keep one dedicated boundary fixture at the actual 200000 cap for scheduled/resource validation; do not inflate every default test to maximum dimensions.
- **Config/internal resources:** assert default quantization disabled/None; under Auto, check full-precision vectors remain and graph reopen works (upstream threshold tests are `S/src/tuning/auto_tune.rs:108–143`). Instrument pool execution to show the fixed two-worker pool is used. A scheduled stress fixture should record file length, mapped bytes, process RSS, graph/cache overhead and shutdown/cancellation latency for two identities and a rebuild at supported dimension extremes. These measurements, not a byte formula or upstream comments, support any performance/memory claim.
- **Authoritative readiness:** missing/malformed metadata, truncated committed vector storage, stale hash/version/identity and malformed generation metadata produce repair status before a metered search if no healthy documents remain. Mixed healthy/broken state returns healthy hits only, with unavailable count. All local orphan repair/rebuild cases keep embedding calls at zero.
