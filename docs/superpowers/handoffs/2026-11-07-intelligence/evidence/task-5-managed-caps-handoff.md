The recommendations retain **200000 stored records including tombstones**, dimensions **128–4096**, **at most two SrvDB engines**, and **one dedicated owner plus exactly two owner-scoped Rayon workers**. ## Fixed policy recommended

| Item | Recommended fixed policy | Normal-growth allowance / interpretation |
| --- | --- | --- |
| Stored records per engine | `N = 200000`, including tombstones | Replacement appends another record; deletion does not reclaim a slot. Reserve the whole incoming batch with checked arithmetic before mutation. |
| Dimensions / element size | `128 <= d <= 4096`, `r = 4*d` bytes, f32 only | Exact identity dimension; no SQ8/PQ reinterpretation. |
| Vector header | Exactly 24 bytes, current writer version 4, magic `0x53764442`, quantization 0, index byte 0, six reserved zero bytes | The application creates current-format generations only. Older/foreign formats fail locally rather than being rewritten for compatibility. |
| `vectors.bin` maximum physical length | `V(d) = max(L + floor(L/2), L + 1024*r)`, where `L = 24 + N*r` | Allows the crate's normal byte-capacity growth, including non-record-aligned tail slack. At this N, the first term wins for every supported d. |
| Encoded metadata value | **16 KiB per record**, checked before add/set, including JSON escaping and location | Metadata contains IDs/version/hash/location, not chunk text, title, source file, credentials, or whole transcript; text/title remain in SQLite. This is a proposed location-encoding contract to confirm at Task 5 dispatch. It is not a lower vector-record capacity. |
| `metadata.db` maximum physical length | **16 GiB = 17179869184 bytes** | N * 16 KiB = 3276800000 logical value bytes. The file envelope is 5.24288 times that payload, leaving about 13.90 GB for redb pages, keys/tombstones/state, copy-on-write/free-page/growth overhead. This is deliberately a generous policy cap, **not a proved redb size theorem**. |
| Metadata preventive watermark | **12 GiB** | Before new writes near this watermark, schedule a local new-generation rebuild under the existing overlap policy, without embeddings. Do not lower N or silently discard live rows. A retained source must still be trusted and persist successfully before the existing vector reader may open. |
| `hnsw.graph` maximum physical length | **512 MiB = 536870912 bytes**, including its 24-byte envelope | More than 3 times the computed worst-case default graph payload below. Also validate its structure/parameters; bytes alone do not bound declared collection lengths. |
| Unexpected IVF/quantized artifacts | **Unsupported in a Task 5 generation: fail-local before open** | Pinned Auto chooses Flat/HNSW only and never converts storage. `ivf.index`, SQ8/PQ vector/quantizer/codebook files are not normal Auto growth. Rejecting them does not force HNSW or lower the stated N/d support. |
| Generation directory enumeration | Inspect **at most 16 entries**, then stop with a local anomaly | Use an allow-list: `srvdb.lock`, `vectors.bin`, `metadata.db`, optional `hnsw.graph`, and their known current-writer temporary names. No recursive walk, symlink target open, unknown subdirectory, or unlimited filename accumulation. |
| `srvdb.lock` contents | **<=4 KiB** | The source only opens/locks this file; ordinary contents are empty. Do not delete a lock file to infer or release ownership. |
| Temporary files | `.vectors.bin.tmp <=24 B`; `.metadata.db.tmp <=16 GiB`; `.hnsw.graph.tmp <=512 MiB` | Atomic writes use exactly these names. A clean sealed generation should have none. Presence is handled through the owning intent, not ignored as proof of cleanliness. `*.compact` is unsupported because Task 5 forbids bare source compact. |

If the finalized TextLocation contract requires an encoded metadata value larger than 16 KiB, increase the **per-value limit and metadata file cap together**, retaining the 5.24288 envelope factor or more. Do not truncate location or reduce the 200000-record support to fit this proposal. No established Task 4 field bound was inspected or assumed here.

## Vector cap proof and actual header checks

Source evidence: `S/src/storage/header.rs:3–18,35–37,73–125`; `S/src/storage/record_file.rs:49–91,124–132,193–223`; `S/src/storage/flat.rs:23–29` as documented in the owner handoff.

The current physical capacity C includes the 24-byte header. An append ending at E grows only when `C < E`, and chooses `max(E, C + max(floor(C/2), 1024*r))`. Under the adapter's stored-record cap, `E <= L`. Thus, at any growth event C is less than L and the new capacity cannot exceed `max(L + floor(L/2), L + 1024*r)`. If a previous capacity already exceeds L, no capped append can require another growth. Reopen shrinks to committed logical length. This accommodates batch appends, minimum growth, and reopen/grow cycles, not merely a single-record growth simulation.

| d | Logical length at N | Accepted allocation cap V(d) |
| --- | ---: | ---: |
| 128 | 102400024 B | 153600036 B (~146.48 MiB) |
| 4096 | 3276800024 B | 4915200036 B (~4.58 GiB) |

Before any existing-generation writable open, use a regular-file read handle and exactly 24 header bytes; parse integer fields with checked conversions and checked multiplication/addition. Require the fixed fields above, `d == identity.dimensions`, `H <= N`, `24 + H*r <= physical_length <= V(d)`, and stable file identity/length during inspection. The header count H is the last vector sync count; **it is not the authoritative committed redb count**. A sealed clean generation also requires H and its sealed committed count to agree.

Do **not** require `(physical_length - 24) % r == 0`: the capacity growth uses bytes, so ordinary allocated tails may be misaligned. Do **not** require physical-present-record count to be <=N; up to roughly 1.5N capacity is legitimate slack. Require that there are enough bytes for H records, not that every allocated byte is a live record. Reject a short committed file; do not rely on the library's `header.count.min(present)` clamp to silently hide truncation.

SrvDB's header validation is weaker than this application policy: it checks magic, rejects newer versions and dimensions outside 1–4096; it does not bound count, require the current version, or check every mode/index/reserved byte. `RecordFile::open` maps the **entire allocated file before recovery**. These checks therefore precede `SrvDB::new_with_config`, not `count()` after it.

## Graph cap and bounded format checks

Evidence: `S/src/index/hnsw/mod.rs:28–66,84–109,176–182,206–231`; `S/src/index/hnsw/links.rs:31–58`; `S/src/index/hnsw/graph.rs:72–90`; `S/src/storage/format.rs:3–16,22–31,34–77`; `S/src/tuning/auto_tune.rs:29–42`.

Auto builds HNSW with the default `m=16`, `m_max=16`, `m_max0=32`, `ef_construction=200`, `ef_search=50`, `use_quantization=false`, and finite default ml. The random level is **capped at 16**, so there are at most 17 neighbor lists. Link maintenance prunes each completed list to 32 neighbors at level zero and 16 at higher levels. Tombstoned nodes still count. A worst-case node has `32 + 16*16 = 288` neighbor IDs.

For the current postcard payload, an ID below 200000 occupies at most three varint bytes. A conservative per-node maximum is `3(map key)+3(node id)+1(level)+1(list count)+17(list lengths)+288*3 = 889 B`. Including the map length, entry point, max level, default config and 24-byte envelope yields approximately **177800043 B** for N nodes. The recommended 512 MiB envelope leaves a factor of approximately **3.02**. This is an encoded-storage calculation, not the heap size of HashMaps, nested Vec capacities, locks, or simultaneous serialization buffers.

Check length before reading a graph in bulk. For a graph allowed into the load path, validate `SRVD`, kind `HNSW`, current payload version 1, zero reserved bytes, checked `payload_len == file_len-24`, and CRC32. A bounded streaming structural walk can validate postcard collections **before materializing them**: at most N unique nodes; map key equals node id; IDs in range; level<=16; exactly level+1 neighbor lists; list limits32/16; bounded in-range IDs; valid entry point/top level; and the approved config. A bitset/owned set bounded by N is sufficient to check duplicate/prefix coverage. Require dense prefix IDs `0..k`, k<=committed count for a graph that the library will extend, because `attach_hnsw` infers missing IDs from `index.len()..count()` rather than inspecting holes.

Do not call unrestricted `HNSWIndex::from_bytes` first and check it afterwards: it deserializes HashMap/nested Vec declarations before validation. Source load also reads the full graph and logs/rebuilds on a decode error (`S/src/engine/open.rs:71–101`), so handing it malformed input is not the desired fail-local path. For the trusted-seal path below, parameters/structure are known from the controlled current writer; any unexpected bytes are rejected before load. A graph validator is a facade/preflight change to implement, **not an existing source guarantee**.

The pin loads `ivf.index` even under a Flat constructor (`S/src/engine/open.rs:57–62`; `S/src/storage/ivf.rs:54–78`). It checks partition count only after allocating/deserializing config, centroid vectors and nested graphs. Task 5 does not generate IVF; reject its presence before open. Do not claim that Flat/quantization-disabled configuration itself suppresses every saved derived index.

## Metadata size is not a safe allocation proof

Evidence: `S/src/storage/metadata.rs:26–38,47–70,94–126,165–178,230–253`; `S/src/engine/open.rs:15–16,55`; `S/src/engine/recover.rs:11–41`.

The source opens/upgrades redb, creates tables, may finish/discard compaction, and performs recovery before returning the engine. Recovery **collects all tombstones into a Vec and then a HashSet** before a caller can check `db.count()`. An externally malformed redb can contain far more tombstones than the vector header count while remaining under a large file cap. Metadata get also creates the whole String before a facade can check the 16 KiB value limit. The source has no application limits on metadata JSON, tombstone cardinality, or state keys.

Consequently, **16 GiB file cap != bounded safe metadata allocation**. The fixed cap limits accepted physical length and hashing work; it cannot by itself certify redb's page declarations, number of keys, or eager allocation. A stricter byte cap would still not provide that proof and would risk rejecting normal capacity. This audit did not inspect a new redb dependency tree or implement an independent redb parser.

The owner handoff's redb default cache setting (up to 1 GiB per database, not eager allocation) remains an additional cost. Neither this setting nor a file cap is a total RSS guarantee. Metadata history/page-growth bounds cannot be proved from SrvDB's thin `Database::create` calls alone. The 5.24-times envelope and 12 GiB watermark are operational recommendations to validate with later real-index resource fixtures, not measured guarantees.

## Trusted generation seal: exact lifecycle recommendation

Because the pinned API cannot safely inspect arbitrary unsealed redb before its writable/recovery open, recommend an application-owned **trusted generation seal in SQLite**, together with a durable dirty/open intent. This is a proposed Task 5 facade/schema requirement, not a provided producer API.

Seal fields: scheme version and pin/format policy; identity and generation; dimension; committed stored count; relative allow-listed filenames; physical byte lengths; and streaming SHA-256 hashes of `vectors.bin`, `metadata.db`, and any `hnsw.graph`. Keep the authoritative seal with SQLite's active-generation/mapping state, not only in an editable adjacent JSON file. A directory name/hash or a sidecar checksum supplied by that directory is not trustworthy provenance. This policy assumes the authoritative application SQLite state is trusted; it is not authentication against an attacker coherently replacing SQLite and index files.

Compute hashes with a fixed buffer (e.g.1 MiB), checked cumulative lengths and owner/generation fencing. No full metadata file Vec. A source owner/maintenance lease fences mutations while reading. Before producing a clean seal, current-writer validation and persisted count/dimension must pass, all metadata inserted by this writer must have been pre-bounded, tombstone IDs must have followed bounded in-range delete operations, and the corresponding SQLite mapping publication must be authoritative. A successful hash alone cannot turn arbitrary external redb into trusted data.

**Fresh empty generation.** Only a new unique managed directory, authorized by a durable creation intent and containing no preexisting payload, may enter the fresh constructor without a seal. It creates bounded current-format state. Validate empty count/dimension, explicitly persist, then publish seal and its generation/mappings transactionally in SQLite. Do not interpret a missing/zero-length file in an existing generation as an empty library: the constructor recreates such files. An interrupted fresh creation is an unsealed staging artifact; it has no authority to become Ready. Its explicit owning intent may permit local discard/recreation of that unpublished artifact, with canonical text/desired rows retained.

**Normal reopen of a clean sealed generation.** Before constructor, enforce file/header caps and verify every sealed base-file length/hash plus approved derived-file state. Then durably mark the generation opening/dirty, retaining its prior seal for provenance, and run the open inside the fixed owner pool. SrvDB open is itself writable: it can truncate allocation slack, perform redb transactions and attach/build derived indexes. Thus post-open bytes may legitimately differ from the prior seal. Check returned dimension/count against the seal, reconcile in bounded passes, call successful persist, and atomically refresh the seal/clear the dirty intent with the authoritative mapping state before exposing the reopened generation as healthy. A timeout observes the retained owner; it does not release a live mapping or directory lock.

**Normal mutation and successful persist.** Write a durable dirty/operation intent **before the first source mutation**. Maintain exclusion/readiness rules so affected documents cannot expose partial new versions. After successful persist and bounded validation, compute the new seal while the engine remains owned, then atomically publish the new seal and Ready/mapping state. Do not update Ready first and seal later. If publication fails, retain the dirty intent and trusted live engine; the state remains non-Ready for the affected operation.

**Partial persist failure with the owner still alive.** Persist may fail after vectors/redb are already durable but before graph save (`S/src/engine/commit.rs:6–37`). The old seal no longer certifies current bytes. Retain the dirty intent, engine/process ownership and original text/files; do not call the operation saved. Because the live engine was built from trusted input and all writes used the bounded adapter, it can locally retry persist/reconcile known orphan IDs and then seal/publish on actual success. No automatic embedding is needed for orphan deletion or valid-vector generation copying. The existing reader may open **only after successful persistence**, with the source SrvDB retaining its lock and a maintenance lease; repeated errors cannot be treated as acknowledgement.

**Crash/owner loss while dirty, partially persisted, or before seal publication.** On restart the source is **unsealed**, even if its header count/length look plausible or a previous seal exists. Do not call the source constructor to discover whether redb will recover safely. Dirty intents name desired work but do not certify arbitrary current redb structure. If another unchanged published sealed generation exists (e.g.rebuild failed before pointer swap), reopen that good generation normally; preserve/isolate the unreferenced staging files for explicit cleanup/recovery. If the only published generation is dirty/unsealed, fail-local as IndexRepairRequired, preserve its source files, SQLite text/desired rows and managed originals, exclude affected generation results, and require explicit repair/reindex into a new generation. The current public facade cannot promise a zero-embedding automatic vector export from that unopened unsafe source. An explicit reindex may call the embedding service using canonical text; startup does not.

**Missing/malformed derived graph with sealed base files.** A missing graph can be rebuilt locally from trusted unchanged vector/redb files after safe source open (the source handles absence; Auto builds a graph). Keep original canonical data and refresh the derived seal after actual persist. A present malformed/unsupported graph must not be passed to the pin's automatic loader. Without a separately authorized staging-copy repair path, fail-local and preserve it. Do not delete/rename the original graph just to make constructor succeed.

**Invalid seal, external file edit, oversized file, dimension/count mismatch, partial header, foreign mode, unexpected compaction/IVF artifact.** Fail-local before writable open/mmap, report safe IndexRepairRequired (ResourceLimit for an attempted supported writer operation exceeding a configured budget), preserve original files/text, and offer explicit repair. Never truncate committed data to the cap, rewrite a header/count to N, silently adopt a smaller dimension, remove metadata, or manufacture an empty index.

There is an intentional stricter restart behavior here: a crash leaves unsealed bytes that the pinned API cannot certify without potentially unsafe allocation/mutation. Relaxing this requires a separately reviewed safe redb preflight/recovery interface or a retained trusted checkpoint/copy protocol; it cannot be achieved by merely checking SrvDB count after open.

## Source mapping and overlap safety remain unchanged

The existing vector-preserving facade is still restricted to a successfully persisted **retained source SrvDB lock + maintenance lease**, an existing nonempty vector file, checked source count/dimension/length, and at most200-record immediate owned copies. No source mutation/remap/persist/close while its auxiliary VectorStorage mapping lives. Drop borrowed slices before destination mutation/yield; drop auxiliary reader and source engine before old-directory cleanup, especially on Windows.

This report **does not authorize** opening VectorStorage directly on an unsafe unsealed source without the retained SrvDB owner. Such a fallback would change the approved safety premise and needs a separate architecture decision; it is not a workaround included in these caps. Nor does it authorize a second source-directory SrvDB, in-place source compact, or a third engine. Rebuild evicts the other idle identity first; source+staging stay<=2 engines. All synchronous engine/preflight work uses the one owner-scoped two-worker pool; no global Rayon pool or detached cleanup is introduced.

## Disk envelope and remaining evidence

At4096 dimensions, final vector+metadata+graph cap per generation is **22631940132 B (~21.08 GiB)**; two final generations are **45263880264 B (~42.16 GiB)**. Those are generous anomaly envelopes, not expected normal utilization. Known atomic temporary files add another metadata/graph cap when actually present; reserve those bytes separately, and reserve staging/old-source coexistence before rebuild. Managed originals, SQLite, other closed identities/history, filesystem overhead and cleanup leftovers are additional. Do not multiply “<=2 open engines” into a claim that only two directories or only this many disk bytes can ever exist.

No exact RAM bound follows: vector mmap capacity can reach4.58GiB per4096-dimensional engine, full graph/tombstone structures and redb cache/transaction allocations coexist, encoding creates payload and envelope buffers, source/staging overlap, and an auxiliary source mapping adds address-space pressure. A source auxiliary mmap does not necessarily duplicate physical pages. These facts are finite policy bounds plus storage arithmetic, not measured RSS/performance.

Later implementation validation should cover: physical slack tail not record aligned; N header with cap slack; N+1/short header/body/wrong dimension/foreign mode; oversized files rejected before any constructor; graph forged collection lengths/config/IDs/levels/CRC; fresh empty seal; clean reopen refreshing byte seals after recovery; dirty marker before mutation/open; persist-error and crash-before-seal cases; successful local retry with retained lock; fail-local unsealed restart preserving originals and zero startup embedding calls; missing graph local rebuild; present bad graph preservation; two-engine rebuild, buffer/batch/pool bounds and real maximum-dimension resource measurements. No test success is claimed by this report.
