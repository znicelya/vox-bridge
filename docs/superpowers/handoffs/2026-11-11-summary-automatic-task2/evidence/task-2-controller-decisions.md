## Pending journal with permanent Existing and unreadable config

Ruling: For pending=1 plus an existing automatic permanent marker and
unreadable configuration, strict read-only Existing may return the original
job, including after Native output deletion, but does not establish bootstrap
or delivery readiness; leave journal/job/counter/version bytes unchanged and
keep startup fenced until a readable config permits its normal disposition
— Task2's bootstrap text expressly requires unreadable config/storage to
retain exact pending journal/readiness fencing; Existing proves no new
admission/payment is needed, not a delivery-ready capability — cost if wrong:
an already summarized history can block intelligence startup until its config
is repaired.

The covering case must prove the same Existing job ID, unchanged pending
journal/counter/version, zero provider calls and no ready publication.

## Same-key close retry

Read `task-2-close-retry-ruling.md` in full. A corrected transient result
failure may be retried or genuinely verified under the same elected key and
actual ack, while the original attempt remains failed in its evidence.
Unresolved effects and sticky native health retain their separate fences.
The actual receipt or lack of an active actor does not discharge a failed
durable write. The ruling's explicit cost and required cases remain part of
the integration review.

## Final App facade disappearance and actual audio ownership

Ruling: A facade-only guard may detect final external service/delivery
facade disappearance without being retained by the worker. It may mark
Closing/live=false, remove its sender/watch ownership, and let natural
channel EOF prove notification/OwnedPermit completion. This is not an
AudioCloseAck, native/inventory join or global process-retirement proof.

Use the proposed narrow App facade composition for final App disappearance:
retain the actual process/File ownership plus audio, orchestrator, admission,
CloseState and narrow delivery ports, without retaining AppState or a strong
SummaryService/JobScheduler in the worker/guard cycle. Elect or reuse the
existing same-key close identity, synchronously fence new audio/runtime
entry, capture the real SessionCloseJoin and AudioBackendCloseJoin, and run
the retained actual audio close owner. Keep delivery drain behind that
actual source; retain every entered child and pre-issued permit. If an
explicit close already owns that key, coalesce with its existing sources /
owner rather than creating a second generation or competing closer.

Global process/File ownership cannot be released while captured native,
inventory, actor/terminal or other admitted work is still pending. Natural
EOF alone cannot discharge those scopes. Existing jobs/index final-drop
owners must still finish their actual work; no other branch may abandon
them. Result/diagnostic/storage failure remains distinct from actual joined
receipt and native quarantine. A failed local journal disposition must
remain truthful/pending and cannot publish ready or a successful close.
Final-facade cleanup may finish with a failure only after actual owners /
readers end; it does not silently promote that outcome to successful rearm.

Inert/no-current-runtime construction is not an exception to the proof rule.
The current capture_close_join and backend begin_close ports can fence their
initialized actual registries and prove genuine empty ownership without
opening native devices or inventory. Use those real inert/empty producers
and their same key. active=None, no live generation or a missing facade
alone must not mint an ack. Unsupported/missing actual sources fail closed.
Preserve inert construction's no cloud/native-service dispatch; do not
start audio or call inventory merely to establish empty ownership.

Cover final App drop with a held native parent after actor/active release,
and independently with held unattached inventory. A same-directory process
lock probe/reopen must remain blocked until the genuine source is released
and cleanup joins; after actual cleanup it can release. Keep the four
established dropped-facade/entered-work lock tests, the held-permit service
case, explicit close/observer-cancellation same-key tests and an inert-drop
case with zero hardware/paid calls. Evidence must identify real producer
completion, not a cached status or a facade strong-count as audio proof.

Basis: Root read the current AppState File owner/intelligence lease, narrow
AutomaticPort/worker and initialized capture_close_join/backend begin_close
producers. The native parent/leaf registry retains its own capacities but
not app.lock; observe may finish/release its terminal sender before actual
native exit. The actual AudioCloseJoin owner explicitly carries process
ownership. Therefore worker EOF can resolve the delivery-cycle defect but
cannot by itself cover final-App native retirement. This is necessary close
ownership in the existing authorized task, not a new product feature.

Cost if wrong: releasing the File/process fence on EOF could allow a fresh
App to enter while old native/inventory resources remain, bypassing the
accepted capacity/epoch/rearm bounds. Retaining the wrong facade in its own
cleanup cycle could instead leak the lock forever. The narrow retained
owner, actual-source hold tests and final independent review must establish
both safe retention and eventual release.

The exact completion validation, real regression evidence and independent

## Final App drop off the original executor thread

Ruling: A final facade dropped on a thread without a current Tokio runtime
must still finish its genuine pending sources when the original entered
executor remains live. Capture a narrow existing executor handle at actual
App/producer entry, including an inert construction followed by first audio
inventory entry. Use it for the same-key capture/AudioCloseJoin start and
subsequent final cleanup, without a strong App/service/jobs cycle or new
service/native entry. Preserve the initialized-empty, no-runtime fast path.

An executor handle does not keep its Runtime alive. A genuinely unavailable
executor, cancellation or lost cleanup task cannot release a pending actual
owner/File or manufacture an AudioCloseAck. Such uncertainty remains fenced;
only real source/worker/child completion discharges ownership. No successful
availability claim is made for a destroyed original executor.

Basis: Root read the full current FinalClose/FinalAppFacade and
AudioCloseJoin::start_owned after the author's self-review. Pending capture
uses Handle::try_current and can fail before the later facade spawn check;
the fallback permanently forgets the File/registries even if their existing
runtime is live elsewhere. The final-facade contract requires eventual
release after genuine cleanup, independently of the external caller thread.
Existing held-source tests on the runtime thread and inert empty-source drop
do not establish this path.

Observe a genuine off-runtime-thread final drop with held native and
unattached inventory sources: lock remains held before release and can be
reacquired only after actual joins. Include inert construction then entered
inventory so constructor-only handle capture cannot satisfy the test. Keep
same-key cancellation/retry, queue/permit and zero-dispatch evidence.

Cost if wrong: caller-thread dependence could leak the process fence after
normal positive cleanup; a cancelled task on a dead executor could instead
release that fence while native work is still pending. Narrow executor and
owner retention plus the actual boundary tests must establish both sides.

## Existing session fixtures versus actual retirement and durable recovery

Ruling: Correct the two047 fixtures to preserve the difference between
logical start reservation release and an independently entered inventory
parent, and between actual native exit and the unresolved original terminal
persistence effect. No production bypass or weakened receipt is authorized.

The cancelled-start fixture keeps immediate active/config reservation release
and zero losing-start native/provider calls. With its original inventory
release still held, a replacement cannot enter native inventory. Only after
that original source is genuinely released/joined may inventory entry2 and
a new successful start occur.

The terminal-write-failure fixture keeps all original attached-waiter error,
missing Completed publication, diagnostic and durable Stopping assertions.
An actual audio receipt cannot discharge the still-installed SQL failure.
Show rejected start and failed original-key effect recovery before repair;
remove the actual injected fault, use the real retry_terminal_close_effects
producer and native/orchestrator key/ack validation/rearm, then demonstrate
successful new start. Keep the original failed attempt's result. Obtain the
key and receipts from actual existing election/join producers.

Basis: Root read047 complete raw evidence and both complete fixtures, the
registered fixture inventory source, fixed inventory parent gate, retained
TerminalFinalization/start fence/recovery, actual App close retry consumer,
and the stable same-key ruling. The first fixture keeps _release alive while
aborting only its observer; the second keeps its Completed-rejecting trigger
installed while asking for a new start. Their old success assertions predate
the binding actual inventory and corrected durable-effect requirements.

Cost if wrong: after a terminal SQL failure, a new session remains unavailable
until the fault is repaired and the original close is recovered. Conversely,
allowing entry before actual inventory join or overwriting that pending effect
could bypass capacity or lose the original same-key recovery. Meaningful
negative/positive boundary assertions and independent final review must judge
both consequences.
