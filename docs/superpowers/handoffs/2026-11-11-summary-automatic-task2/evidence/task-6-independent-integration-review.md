**OO1 — synchronous scheduler SQLite acquisition: supported mechanism and potential effect.** [Scheduler start](/mnt/data/workspack/github/vox-bridge/.worktrees/vox-bridge-implementation/src-tauri/src/intelligence/jobs.rs:277) creates two actual workers and supplies initial claim opportunities. [Worker claim entry](/mnt/data/workspack/github/vox-bridge/.worktrees/vox-bridge-implementation/src-tauri/src/intelligence/jobs.rs:640) calls the synchronous claim function. [Claim SQL acquisition](/mnt/data/workspack/github/vox-bridge/.worktrees/vox-bridge-implementation/src-tauri/src/intelligence/jobs.rs:775) enters the store transaction before checking stopped/closed state or an empty queue. [Store transaction](/mnt/data/workspack/github/vox-bridge/.worktrees/vox-bridge-implementation/src-tauri/src/storage/sqlite.rs:149) acquires `std::sync::Mutex::lock` without an asynchronous yield at that acquisition boundary.

Consequently, if SQLite is held while both workers claim, both may occupy Tokio worker threads waiting for that mutex even with no usable queued job. On an executor with no remaining runnable worker, timer polling, other async work and close observers can be delayed until the independent holder releases SQLite. A fixture that makes release depend on a Tokio timeout can form a starvation cycle. This mechanism is an existing scheduler dependency; I found no reverse recovery-state-to-SQL lock cycle at this held acquisition boundary.
